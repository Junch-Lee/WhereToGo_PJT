## 의사결정 사안들

### 1. AI/백엔드 책임 경계 

제안: AI는 식별자만 출력, 백엔드가 FK 조회+저장
 - Node1/Node2 원칙(ORM 미접근)과 일관
 - AI 출력은 순수 dict (slug, source_row_number, external_id)
 - Django serializer/service가 객체 조회 후 저장

### 3. 단계 - 검색결과 매칭 방식

```
┌─────────────────────────────────────────────────────────────────┐
│  검색된 courses/resources를 어떻게 step에 배치?               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [옵션 A] LLM이 전부 배치 (권장)                              │
│   - 검색 결과 목록(식별자+제목+topic)을 LLM에 제공           │
│   - LLM이 단계 설계 + 각 단계에 적합한 자료 매칭             │
│   ✓ 의미 기반 배치, 자연스러운 커리큘럼                      │
│   ✗ LLM이 식별자를 정확히 인용해야 함 (환각 위험)            │
│                                                               │
│  [옵션 B] LLM은 단계만, 배치는 규칙                           │
│   - LLM은 step 구조만 생성                                   │
│   - topic 매칭으로 자료를 규칙 배치                          │
│   △ 환각 적으나 배치 품질 낮음                              │
│                                                               │
│  → 제안: 옵션 A + 검증 (LLM이 인용한 식별자가              │
│     실제 검색결과에 있는지 후처리 검증, 없으면 제거)        │
│                                                    │
│                                                               │
└─────────────────────────────────────────────────────────────────┘
```

### 7. 빈/부족 결과 처리

제안:
 - is_in_scope=false 또는 검색결과 빈 경우
   → 커리큘럼 생성 스킵, 안내 메시지 반환
 - 검색결과 일부만 있으면 → 있는 만큼으로 생성

#### `is_in_scope=false`의 경우, 제안 된 방안처럼 커리큘럼 생성 대신 안내 메세지 제공 후 다시 선택하게끔 하는 장치 등이 필요할 것으로 예상됨.
