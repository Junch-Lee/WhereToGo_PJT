문서 개요

본 문서는 WhereToGo 프로젝트의 기획, 요구사항, 시스템 설계, AI/RAG 설계, 데이터베이스 설계, API 계약, 프론트엔드 화면 구성, 학습 실행 설계, 테스트 및 협업 방식을 하나로 정리한 제출용 통합 문서이다.

원본 설계서의 방향성을 유지하되, 최종 코드와 대조하여 실제 구현과 다른 초기 기획 항목은 “향후 고도화”로 이동하고, 실제 구현된 학습 대시보드 API, 스트리밍 생성 UX, 데모 데이터 seed 등 누락된 구현 사항을 반영했다.

작성 원칙

  • 실제 코드에 존재하는 모델, API, 화면, 서비스 계층을 우선 기준으로 삼는다.
  • 구현되지 않은 면담 세션 DB, 진단 퀴즈, 학습 노트 전용 모델은 핵심 구현에서 제외하고 향후 확장으로 둔다.
  • AI가 만든 자연어 결과를 그대로 저장하지 않고, 검색 결과 식별자와 FK 변환을 통해 데이터 무결성을 확보한 구조를 설명한다.
  • 배포 인프라는 현재 확정 구현이 없으므로 로컬 실행 기준과 미배포 상태를 명시한다.

1. 프로젝트 개요와 문제 정의

1.1 서비스 한 줄 정의

WhereToGo는 사용자의 학습 목표와 현재 조건을 바탕으로 실제 교육 데이터에 근거한 커리큘럼과 학습 자료를 추천하고, 학습 시작 이후 진행 상태까지 관리하는 개인 학습자용 AI 교육 컨설턴트 서비스이다.

1.2 문제 배경

학습자는 새로운 기술이나 분야를 배우려 할 때 무엇부터 시작해야 하는지, 어떤 자료가 적합한지, 어느 순서로 학습해야 하는지를 먼저 결정해야 한다. 이 과정은 학습 그 자체보다 많은 탐색과 판단을 요구하며, 특히 잘 모르는 분야일수록 계획 수립 단계에서 이탈하기 쉽다.

범용 생성형 AI를 사용하더라도 같은 목표에 대해 결과가 크게 달라질 수 있고, 실제로 존재하지 않는 자료를 추천하거나 학습 순서와 난이도가 일관되지 않는 문제가 발생한다. 따라서 본 프로젝트는 “학습 계획 수립의 인지 비용”과 “AI 추천의 신뢰성”을 동시에 해결하는 것을 목표로 한다.

1.3 핵심 문제 정의

문제발생 결과설계 대응
시작점 불명확학습 목표는 있으나 첫 행동으로 이어지지 않음질문 흐름과 단계별 로드맵 자동 생성
탐색 비용 과다강의와 문서를 비교하는 데 많은 시간 소요교육 데이터 검색과 추천 자료 연결 자동화
수준·시간 미반영과도하거나 부족한 학습량수준, 기간, 주간 가능 시간을 입력으로 반영
순수 LLM 불안정성할루시네이션과 결과 일관성 저하Topic Catalog, RAG 검색, 식별자 검증 결합
계획과 실행의 단절생성된 커리큘럼이 실제 학습 관리로 이어지지 않음StepProgress, Schedule, Progress 모델 분리

2. 목표·범위·성공 기준

2.1 목표 서비스

  • 사용자의 학습 목표, 목적, 수준, 기간, 주간 가능 시간, 선호 학습 방식을 입력받는다.
  • 보유한 강의계획서와 공개 강좌 데이터를 RAG로 검색한다.
  • 검색 결과를 근거로 단계별 커리큘럼, 추천 강의, 추천 학습 자료를 생성한다.
  • 사용자가 preview를 확인한 뒤 저장하면 실제 DB row로 반영한다.
  • 저장된 커리큘럼을 시작, 일시정지, 재개, 완료할 수 있다.
  • 학습 대시보드에서 현재 학습, 진행률, 최근 활동, 로드맵을 확인한다.

2.3 성공 기준

  • 동일한 사용자 입력에 대해 실제 존재하는 강의/자료 식별자를 기반으로 커리큘럼이 생성된다.
  • 생성 결과에 검색 결과에 없는 course/resource identifier가 포함되면 제거되거나 저장되지 않는다.
  • 사용자는 생성 중 progress bar와 문구를 통해 서비스가 동작 중임을 인지할 수 있다.
  • 학습 시작 시 전체 미래 일정을 만들지 않고 현재 Step 일정만 생성한다.
  • 대시보드에서 진행 중, 완료, 일시정지, 초안 커리큘럼 상태가 구분된다.

3. 사용자와 서비스 시나리오

3.1 핵심 사용자

사용자상황필요
취업 준비 학습자포트폴리오를 만들고 싶지만 학습 순서가 불명확함실습 중심 커리큘럼과 추천 강의
전환 학습자비전공 또는 다른 분야에서 데이터/AI로 이동하려 함초급 개념부터 단계별 자료
반복 학습자여러 커리큘럼을 병행하거나 중단 후 재개함현재 학습과 진행률 대시보드

3.2 주요 시나리오

  1. 사용자가 홈 화면에서 학습 목표를 입력한다.
  2. /chat 화면에서 목적, 수준, 기간, 주간 가능 시간, 선호 학습 방식을 선택한다.
  3. /interview/summary에서 답변을 확인하고 커리큘럼 생성을 요청한다.
  4. 백엔드는 streaming API로 진행 상태를 전달하고 프론트는 progress bar와 문구를 갱신한다.
  5. 생성 결과는 /curriculum/result에서 preview로 표시된다.
  6. 사용자가 저장하면 /api/curriculums/save-generated/가 호출되어 DB에 반영된다.
  7. 사용자는 /curriculum/:id에서 학습을 시작하고 Step 완료를 기록한다.
  8. /learning 대시보드에서 현재 학습, 최근 활동, 진행률을 확인한다.

7. AI·RAG·Agent 설계

7.1 RAG + Agent 선택 이유

대안장점한계판단
Rule-based결과가 명확함새 목표와 맥락 확장에 약함보조 검증
Keyword search빠르고 단순함동의어, 순서, 난이도 반영 부족Topic 매칭 보조
Pure LLM자연어 생성 품질 높음할루시네이션, 실제 자료 존재 여부 문제단독 사용하지 않음
RAG + Agent근거 검색과 단계별 판단 가능데이터 품질과 검증 로직 필요최종 채택

7.2 실제 구현 흐름

사용자 입력
  -> CurriculumGenerateSerializer.to_raw_input()
  -> build_topic_catalog()
  -> ai.agent.run_agent(raw_input, catalog)
  -> input_analysis node
  -> search node
  -> curriculum generation node
  -> identifier validation
  -> normalize_agent_response()
  -> preview 반환 또는 save-generated 저장

7.3 RAG 설정

  • Vector DB: ChromaDB
  • Collection: courses, resources
  • Embedding: text-embedding-3-small
  • Chat model: gpt-4o-mini
  • 문서 단위: CSV row 하나를 하나의 검색 문서로 사용

8.1 Topic 구축 정책

  • MVP 기준 최대 depth는 3으로 제한한다.
  • 표준명은 한국어 중심으로 두고, 영어/약어/변형 표현은 alias로 관리한다.
  • 새 후보를 즉시 topics에 넣지 않고, 후보 검토 pipeline을 거친다.
  • LLM은 topic 매칭과 후보 추천을 보조하되 자동 승인하지 않는다.

10. 커리큘럼 생성·저장 설계

10.1 생성 입력

프론트는 목표, 목적, 난이도, 기간, 주간 가능 시간, 선호 학습 방식을 전송한다. 백엔드는 CurriculumGenerateSerializer로 검증한 뒤 Agent 입력인 raw_input으로 변환한다.

10.2 Preview와 Save 분리

AI 생성 결과는 곧바로 DB에 저장하지 않는다. 생성 API는 사용자가 확인할 preview payload를 반환하고, 사용자가 저장을 선택하면 /api/curriculums/save-generated/에서 transaction으로 저장한다.

  • 장점: 잘못된 AI 결과가 사용자 DB에 바로 남지 않는다.
  • 장점: 저장 전 화면에서 강의/자료 preview를 확인할 수 있다.
  • 장점: FK 조회와 transaction을 저장 service에 집중시킬 수 있다.

10.3 StreamingHttpResponse 적용

커리큘럼 생성은 RAG 검색과 LLM 호출 때문에 시간이 걸릴 수 있다. 백엔드는 StreamingHttpResponse로 progress, done, error 이벤트를 전송하고, 프론트는 fetch와 ReadableStream으로 chunk를 읽어 progress bar와 문구를 갱신한다.

단계progress설명
입력 검증10요청 body 검증
Topic catalog 구성25AI Agent에 전달할 topic 후보 구성
Agent 실행45RAG 검색과 LLM 생성
결과 정규화80응답 payload 구성
완료100최종 결과 반환
실제 구현에서는 별도 generation_id 상태 조회 API가 없다. 따라서 원본 설계서의 generation 상태 조회는 향후 고도화 항목으로 분리한다.

11. 학습 시작·일시정지·완료 설계

11.1 초기 설계와 문제

초기에는 커리큘럼 시작 시 모든 Step의 미래 일정을 한 번에 생성하려 했다. 그러나 사용자가 중간에 일시정지하거나 특정 Step에 예상보다 오래 걸릴 경우, 이후 모든 일정이 무효화되고 일정 테이블이 상태와 진행률까지 떠안는 문제가 생겼다.

11.2 최종 의사결정

전체 계획은 curriculum_steps에 먼저 저장하되, learning_schedules는 사용자가 실제로 시작한 현재 Step에 대해서만 생성한다. Step 실행 상태는 CurriculumStepProgress, 실제 기록은 LearningProgress가 관리한다.

11.3 상태 흐름

대상상태 흐름
CurriculumDRAFT -> ACTIVE -> PAUSED -> ACTIVE -> COMPLETED
StepProgressNOT_STARTED -> IN_PROGRESS -> PAUSED -> IN_PROGRESS -> COMPLETED
LearningSchedulePLANNED -> DONE 또는 PLANNED -> CANCELLED
LearningProgressIN_PROGRESS, PAUSED, PARTIAL, COMPLETED

18. 한계와 향후 고도화

18.1 현재 한계

  • 교육 데이터는 컴퓨터공학/AI 분야 중심이므로 다른 도메인 품질은 추가 검증이 필요하다.
  • 추천 품질의 정량 평가 데이터셋과 사용자 실험 데이터가 제한적이다.
  • 차시/영상 구간 단위까지 세밀하게 연결되지는 않았다.
  • 백엔드 면담 세션 저장, 진단 퀴즈, topic별 사용자 숙련도 모델은 아직 구현되지 않았다.
  • 비동기 작업 큐와 운영 배포 구조는 확정 구현 범위가 아니다.

18.2 고도화 우선순위

우선순위고도화기대 효과
1추천 평가 데이터셋 구축검색, 순서, 난이도 품질 정량 비교
2비동기 Job Queue 및 generation 상태 조회연결 단절/장시간 처리 대응 강화

5학습 기록 기반 자동 재조정실제 속도와 난이도에 맞춘 개인화
6관리자 Topic/추천 품질 워크플로후보 검수와 오류 수정 효율화
7배포 인프라 확정운영 환경, 로그, 백업, CI/CD, HTTPS 구성
